# Disposable beta data

This dataset replaces all application data in an explicitly acknowledged beta, development or test database. It keeps Flyway history and schema, Docker volumes and object storage. Never use it on production or a shared database with retained data.

1. Point the API `.env` at the intended disposable Compose project/database. Allowed database names are `mydatabase` (the existing local default), `cashly`, `cashly_beta`, `cashly_dev`, `cashly_test`; environment must be `beta`, `dev` or `test`. The database argument must match both the container's `MYSQL_DATABASE` and SQL `DATABASE()`.
2. Start MySQL and the API normally so Flyway applies the complete schema (including V26 and V27), then stop API traffic: `docker compose --env-file .env stop app`. Confirm the service name in your Compose configuration if using an override.
3. From `cashly-api`, run `./scripts/reset-beta-data.sh beta mydatabase` (substitute your exact environment/database). This is the explicit destructive action; it is not executed automatically on startup. Do not use mysql `--force` or bypass the master loader.
4. Require exit code zero and `Cashly beta seed integrity passed`; restart the API, sign in and perform the access checks below. On any failure, leave traffic stopped, fix the cause and rerun the complete reset. Do not attempt individual seed retries.
5. Repeat step 3 once to verify clean-reset repeatability. IDs, references, roles and amounts are deterministic; operational fixture dates may use current timestamps.

`db/seed.sql` guards its target before deleting anything. `00_reset.sql` clears **all** application tables in child-before-parent order, preserving the migration-created administration lock singleton and including notifications, refresh tokens, source links, category snapshots, cash movements, sequence rows and bootstrap references. Foreign-key checks remain enabled throughout loading. The script expands the master loader into a single SQL batch before execution; MySQL batch mode stops on the first error. Reset/load is deliberately not claimed to be atomic: MySQL DDL and temporary integrity procedures can commit, and a failed load requires another full reset. Helper procedures are recreated on every invocation so a failed assertion can be retried after fixing its cause.

Load order: access references → users → customers → categories → warehouses → products → canonical price types/prices → orders → invoices → quotes → payment methods → payments → notes → returns → stock opening → cash registers → purchases → derived stock/receivable balances → integrity assertions. `05b_price_types_and_product_prices.sql` is the sole price-type source; the conflicting `06_price_types.sql` was removed.

The six historical users keep their IDs and usernames so business references continue to resolve. All have complete names, address and a single phone number, active department/role assignments and the existing beta password documented in `01_users.sql`. `superadmin@cashly.com` is a protected system administrator; `admin@cashly.com` uses an editable administrator role. `demo@cashly.com` uses an ordinary configurable demonstration role: no INVENTORY access, CATALOG READ only, and READ for the other selected business modules. This is an example matrix, never a hardcoded policy: change any module/action combination through Roles. The operational `Sales` role additionally has INVENTORY READ/EXECUTE: sales stock reservations require inventory execution, and detail views containing stock require inventory consultation. A role with only its own module READ can access permitted lists, while stock-rich details also require INVENTORY READ; the demo intentionally cannot open those details.

Verify administrator login, Roles/Departments CRUD and user selects. Verify demo navigation and direct API denials for inventory and catalog mutations, then modify another arbitrary module in its role and verify an already-issued token immediately follows the new grant. Verify the app refreshes permissions after a denial/session restoration.

Business fixtures now reconcile invoice/quote totals, return source prices, note customer ownership and payment applied amounts. Stock uses deterministic 10,000-unit opening entries for every active warehouse/simple product and derives exits, returns, confirmed purchase entries, reservations and cumulative balances from actual allocations. Customer credit is the sum of return credits and unapplied approved payment advances. Historical June cash register examples have empty, zero-valued summaries because the dataset has no receipts in that period; no fabricated cash totals remain.

`99_integrity.sql` fails on declared FK orphans, incomplete profiles, unsupported module/action combinations, malformed demo grants, header/line totals, returned quantity/price/source mismatches, payment allocation ownership, balance ledger mismatches, stock arithmetic and register totals. These SQL checks plus two successful real MySQL resets, fresh Flyway startup and login/API smoke tests are required verification; static inspection alone is insufficient.
